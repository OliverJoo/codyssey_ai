# b1-2 평가문항 질문과 답변

이 답변은 `b1-2.pdf`, 제공된 `agent-leak-app` ARM64 실제 실행, `04_monitor.sh` 출력 형식을 기준으로 작성했다. PID·타임스탬프·세부 수치는 실행마다 달라지므로 제출 전 자신의 번호가 붙은 증거 로그로 교체한다.

## 항목 1: 결과물 충족 여부

### 질문 1-1

**Q. [OOM] 메모리 사용량이 선형적으로 증가하다가 프로세스가 강제 종료되는 패턴이 로그에 기록되어 있는가?**

**A.** 그렇다. `07_evidence_oom-before.log`에서 관제 CSV의 `RSS_KB`/`MEM_MB`가 시간에 따라 증가하고, 앱 로그는 `Current Heap: 25MB` → `50MB` 순으로 증가한다. 이어 `Memory limit exceeded (50MB >= 50MB)`와 `Self-terminating process PID`가 기록되고 관제 마지막에 같은 PID의 `EXITED`가 남는다. 내부 힙 수치와 OS의 RSS는 측정 기준이 달라 정확히 같지는 않지만 둘 다 증가 방향이어야 한다.

**관련 파일:** [Before 증거](./07_evidence_oom-before.log) · [OOM 리포트](./09_report_oom.md) · [관제 스크립트](./04_monitor.sh)

### 질문 1-2

**Q. [OOM] `MEMORY_LIMIT` 조정 후 프로세스 생존 시간이 늘어난 Before & After 비교 결과가 있는가?**

**A.** 있다. Before는 50MB, After는 100MB로 한 변수만 바꾼다. 제공 앱은 약 3초마다 내부 힙을 25MB씩 늘리므로 50MB 실행은 약 5초, 100MB 실행은 그보다 늦게 제한에 도달한다. 정확한 비교는 두 파일의 `STARTED_AT`, 마지막 관제 `ELAPSED`, `TIMED_OUT`, 종료 로그 시각으로 계산한다. 제한 상향은 종료를 늦출 뿐 누수를 해결하지 않는다.

**관련 파일:** [Before 증거](./07_evidence_oom-before.log) · [After 증거](./08_evidence_oom-after.log) · [OOM 리포트](./09_report_oom.md)

### 질문 1-3

**Q. [CPU] CPU 사용률이 임계치를 초과하여 프로세스가 종료되는 패턴이 로그에 기록되어 있는가?**

**A.** 앱의 보호 로직 관점에서는 있다. `10_evidence_cpu-before.log`에서 내부 `Current Load`가 5.00%에서 50.15%까지 증가했고 `CPU Threshold Violated!` 다음에 종료되었다. 다만 같은 PID를 추적한 관제 CSV의 OS 실측 `CPU_PERCENT`는 시작 직후 3.0%를 제외하면 주로 0.5~1.0%였다. 따라서 이 바이너리는 내부 CPU 부하 시나리오와 종료 패턴을 재현하지만, 실제 코어 점유율이 50%였다고 해석하면 안 된다. 실제 장애 조사에서는 앱 지표와 `ps`/`top` 실측값을 반드시 구분한다.

**관련 파일:** [Before 증거](./10_evidence_cpu-before.log) · [CPU 리포트](./12_report_cpu.md) · [관제 스크립트](./04_monitor.sh)

### 질문 1-4

**Q. [CPU] `CPU_MAX_OCCUPY` 조정 후 종료 여부/생존 시간이 변한 Before & After 비교 결과가 있는가?**

**A.** 있다. Before는 100으로 높은 부하를 허용해 약 50% 보호 기준까지 상승한 뒤 종료되고, After는 10으로 제한해 5~10% 사이에서 `Peak reached` → `Starting cooldown` → `Cooldown complete`를 반복하며 실험 제한 시간 동안 생존한다. 두 로그의 `PROCESS_EXIT_STATUS`, `TIMED_OUT`, `ELAPSED`를 함께 비교한다.

**관련 파일:** [Before 증거](./10_evidence_cpu-before.log) · [After 증거](./11_evidence_cpu-after.log) · [CPU 리포트](./12_report_cpu.md)

### 질문 1-5

**Q. [Deadlock] 프로세스가 살아있으나(PID 존재) CPU/메모리 변화 없이 로그가 멈춘 상태를 식별했는가?**

**A.** 그렇다. `13_evidence_deadlock-before.log`에는 `PID`가 기록되고 관제 루프가 제한 시간까지 같은 PID를 계속 표본화한다. 앱 로그는 두 `WAITING ... (Status: BLOCKED)` 이후 진행되지 않으며 작업 완료 로그가 없다. `TIMED_OUT=true`는 프로세스가 스스로 끝나지 않았음을 뜻한다. PID 존재 하나만으로는 부족하고, 자원 변화 정체와 로그 정지를 함께 봐야 한다.

**관련 파일:** [Before 증거](./13_evidence_deadlock-before.log) · [Deadlock 리포트](./15_report_deadlock.md) · [관제 스크립트](./04_monitor.sh)

### 질문 1-6

**Q. [Deadlock] `MULTI_THREAD_ENABLE` 조정 후 데드락 재현/회피 비교 결과가 있는가?**

## 항목 2: 명령과 판단 과정

### 질문 2-1

**Q. `04_monitor.sh`에서 메모리 증가 패턴을 추적하기 위해 사용한 명령어와 데이터 추출 방법은 무엇인가?**

**A.** 먼저 `kill -0 PID`로 프로세스 생존 여부를 확인한다. 살아 있으면 `ps -p PID -o %cpu=,rss=,stat=,nlwp=,etime=`로 CPU%, RSS(KB), 상태, 스레드 수, 경과 시간을 한 번에 읽는다. `awk`로 `RSS / 1024`를 계산해 MB로 만들고 `date -Iseconds` 타임스탬프와 함께 CSV로 출력한다. 1초 간격 표본에서 `MEM_MB`를 시간 순으로 비교하면 증가율을 볼 수 있다. Linux VM에서는 `watch -n 1 'ps ...'`, `top -p PID`, `/proc/PID/status`의 `VmRSS`도 교차 확인에 쓸 수 있다.

**관련 파일:** [관제 스크립트](./04_monitor.sh) · [OOM 증거](./07_evidence_oom-before.log)

### 질문 2-2

**Q. 프로세스의 CPU 사용률을 확인하기 위해 선택한 도구와 적용한 옵션의 의미를 구분하여 설명할 수 있는가?**

**A.** 자동 수집은 `ps -p PID -o %cpu=`를 사용한다. `-p`는 대상 PID만 선택하고, `-o`는 출력 열을 지정하며, 열 이름 뒤 `=`는 헤더를 없애 파싱하기 쉽게 한다. 순간 변화와 스레드별 차이는 `top -H -p PID`로 본다. `-H`는 스레드 단위, `-p`는 특정 프로세스만 표시한다. 고정된 증거에는 `ps`, 실시간 관찰에는 `top`이 적합하다.

**관련 파일:** [관제 스크립트](./04_monitor.sh) · [CPU 리포트](./12_report_cpu.md)

### 질문 2-3

**Q. 프로세스가 "살아있지만 멈춰있는 상태"를 어떤 도구 순서와 판단 흐름으로 진단했는가?**

**A.** 순서는 다음과 같다.

1. `pgrep -af agent-leak-app` 또는 `ps -ef`로 PID가 존재하는지 확인한다.
2. `ps -p PID -o stat,etime,%cpu,rss,nlwp`를 여러 번 실행해 PID는 유지되지만 CPU/RSS가 정체하는지 본다.
3. `ps -L -p PID ...` 또는 `top -H -p PID`로 개별 스레드도 진행하지 않는지 확인한다.
4. 앱 로그의 마지막 줄과 타임스탬프를 확인해 출력이 멈춘 지점을 찾는다.
5. `LOCK ACQUIRED`, `Need resource`, `WAITING ... BLOCKED`를 시간순으로 연결해 A→B, B→A 순환 의존을 만든다.

이 다섯 증거가 맞을 때 데드락으로 판단한다. 단순히 CPU가 0%라는 이유만으로는 정상적인 I/O 대기나 유휴 상태와 구분할 수 없다.

**관련 파일:** [Deadlock 증거](./13_evidence_deadlock-before.log) · [Deadlock 리포트](./15_report_deadlock.md) · [관제 스크립트](./04_monitor.sh)

## 항목 3: 운영체제 개념 설명

### 질문 3-1

**Q. 메모리 누수가 발생했을 때 애플리케이션의 메모리 보호 정책이 해당 프로세스를 강제 종료하는 이유는 무엇인가?**

**A.** 한 프로세스의 누수가 계속되면 물리 메모리와 스왑이 줄고 다른 서비스까지 느려지거나 운영체제 OOM Killer가 임의의 프로세스를 종료할 수 있다. MemoryGuard가 임계치에서 문제 프로세스를 먼저 종료하면 장애 범위를 해당 프로세스로 제한하고 시스템 전체 불안정을 예방할 수 있다. 데이터 손실이나 재시작 비용이 있지만 전체 서버가 멈추는 것보다 작은 피해를 선택하는 보호 장치다.

**관련 파일:** [OOM 리포트](./09_report_oom.md) · [OOM Before 증거](./07_evidence_oom-before.log)

### 질문 3-2

**Q. CPU 과점유 시 단일 프로세스를 종료하는 것이 시스템 보호에 왜 필요한가?**

**A.** CPU 코어는 여러 프로세스가 시간 조각을 나눠 쓴다. 한 프로세스가 계산 루프를 계속 돌면 다른 요청이 실행될 차례가 늦어지고 지연시간이 커진다. 과점유 프로세스를 제한하거나 종료하면 스케줄러가 다른 중요한 프로세스에 CPU 시간을 줄 수 있어 서버 전체의 응답성을 회복한다. 운영 환경에서는 즉시 종료 전 nice/cgroup 제한, 속도 제한, 재시작 정책도 고려한다.

**관련 파일:** [CPU 리포트](./12_report_cpu.md) · [CPU Before 증거](./10_evidence_cpu-before.log)

### 질문 3-3

**Q. 교착상태가 발생하는 원리를 "상호 배제"와 "순환 대기" 개념으로 설명할 수 있는가?**

**A.** 상호 배제는 한 자원을 동시에 한 스레드만 가질 수 있다는 뜻이다. 이 앱에서 Thread-1은 A를, Thread-2는 B를 독점한다. Thread-1이 B를 기다리고 Thread-2가 A를 기다리면 대기 화살표가 Thread-1 → B/Thread-2 → A/Thread-1의 원을 만든다. 자원을 강제로 빼앗지 못하고 기존 자원을 놓지 않으므로 둘 다 영원히 진행하지 못한다.

**관련 파일:** [Deadlock 리포트](./15_report_deadlock.md) · [미션 흐름도](./02_mission-flow.svg)

### 질문 3-4

**Q. 로그에서 스레드 간 순환 의존 관계(A→B, B→A)를 어떻게 파악했는가?**

**A.** 각 스레드의 `LOCK ACQUIRED`를 먼저 표로 적어 현재 소유자를 정한다. 다음 `Need resource` 또는 `WAITING` 로그로 필요한 자원을 적는다. Thread-1은 A를 보유하고 B가 필요하며, Thread-2는 B를 보유하고 A가 필요하다. 소유자에서 대기 대상으로 화살표를 그렸을 때 서로 되돌아오는 폐곡선이 생기므로 순환 대기라고 판단했다.

**관련 파일:** [Deadlock 증거](./13_evidence_deadlock-before.log) · [Deadlock 리포트](./15_report_deadlock.md)

## 항목 4: 응용·회고 질문

### 질문 4-1

**Q. 실제 운영 서버에서 메모리 누수를 장애 전에 탐지하도록 현재 `04_monitor.sh`를 어떻게 개선하겠는가?**

**A.** 단일 수치를 저장하는 수준에서 다음 기능을 추가한다.

- RSS 절대값과 5분 이동 증가율(MB/min)을 함께 계산한다.
- 연속 N회 임계 초과 때만 경고해 순간 스파이크 오탐을 줄인다.
- PID 재시작을 구분하도록 시작 시각과 실행 파일을 함께 기록한다.
- cgroup 메모리, 호스트 가용 메모리, 스왑, OOM 이벤트도 수집한다.
- CSV를 Prometheus node/process exporter 또는 로그 수집기로 보내 대시보드와 알림을 만든다.
- 경고 시 `ps`, `/proc/PID/status`, 열린 파일 수, 최근 앱 로그를 자동 스냅샷으로 남긴다.

예를 들어 RSS가 10분 연속 분당 20MB 이상 증가하고 예상 한계 도달 시간이 15분 이하면 경고하도록 한다. 절대 임계치만 보는 것보다 장애 전 탐지가 빠르다.

**관련 파일:** [관제 스크립트](./04_monitor.sh) · [OOM 리포트](./09_report_oom.md)

### 질문 4-2

**Q. OOM, CPU Spike, Deadlock 중 실제 서비스 환경에서 가장 치명적인 것은 무엇이며 어떻게 근본 예방하겠는가?**

**A.** 서비스 특성에 따라 다르지만, 관제에서 놓치기 쉬운 Deadlock을 가장 위험하게 본다. 프로세스와 포트가 살아 있어 단순 liveness 검사는 통과하지만 실제 요청은 끝나지 않아 장애 발견이 늦어질 수 있기 때문이다. 근본 예방은 전역 락 순서 규칙, 짧은 임계구역, 락 타임아웃, 락 보유 중 I/O 금지, 동시성 테스트, 요청 완료를 확인하는 readiness/외부 합성 모니터링이다. OOM과 CPU에도 각각 메모리 상한·누수 테스트와 CPU 프로파일링·속도 제한이 필요하다.

**관련 파일:** [OOM 리포트](./09_report_oom.md) · [CPU 리포트](./12_report_cpu.md) · [Deadlock 리포트](./15_report_deadlock.md)

### 질문 4-3

**Q. 같은 서버에서 OOM과 Deadlock이 동시에 발생했다면 어떤 순서로 트러블슈팅하며 그 근거는 무엇인가?**

**A.** 먼저 증거를 보존한 뒤 메모리 고갈 확산을 막고, 그 다음 데드락을 분석한다.

1. 시각, PID, cgroup/호스트 메모리, `ps`, 스레드 상태, 앱 로그를 즉시 저장한다.
2. 메모리 여유가 거의 없으면 문제 인스턴스를 트래픽에서 제외하고 제한·재시작으로 시스템 전체 OOM을 막는다. 메모리 고갈은 다른 프로세스까지 연쇄 종료시킬 수 있어 우선순위가 높다.
3. 복제 인스턴스가 있으면 서비스 연속성을 확보한다.
4. 저장한 스레드/락 로그로 순환 대기를 분석하고 데드락 코드를 수정한다.
5. 메모리 누수와 데드락을 각각 독립된 실험으로 재현해 원인이 서로 섞이지 않았는지 확인한다.

재시작부터 하면 원인 증거가 사라지므로 항상 짧은 증거 수집이 첫 단계다. 단, 서버 전체가 곧 멈출 정도면 가용성 보호를 우선하고 가능한 최소 증거만 수집한다.

**관련 파일:** [OOM 리포트](./09_report_oom.md) · [Deadlock 리포트](./15_report_deadlock.md)

### 질문 4-4

**Q. 환경변수 조정이 임시 조치라면 소스 코드를 직접 수정할 때 장애 유형별로 무엇을 개선하겠는가?**

**A.** OOM은 사용이 끝난 객체 참조 제거, 무제한 컬렉션/캐시의 크기·TTL 제한, 스트리밍 처리, 메모리 프로파일 회귀 테스트를 적용한다. CPU는 바쁜 대기 제거, 블로킹/이벤트 기반 대기, 작업 큐 backpressure, 알고리즘 복잡도 개선, 취소 가능한 루프를 적용한다. Deadlock은 전역 락 순서 통일, 중첩 락 축소, `tryLock` 타임아웃, 불변 데이터나 메시지 전달 사용, 락 순서 테스트를 적용한다.

**관련 파일:** [OOM](./09_report_oom.md) · [CPU](./12_report_cpu.md) · [Deadlock](./15_report_deadlock.md)

### 질문 4-5

**Q. 다시 처음부터 수행한다면 트러블슈팅 과정을 어떻게 다르게 접근하겠는가?**

**A.** 먼저 정상 기준 실행을 남기고, 실험표를 만들어 한 번에 한 변수만 바꾼다. 모든 실행에서 PID·시작 시각·환경변수·종료 코드를 자동 기록하고, 관제와 앱 로그의 시계를 맞춘다. 각 장애의 성공 판정 조건을 실행 전에 적고, 동일 시간 제한으로 반복한다. 마지막에 리포트를 쓰는 대신 실험 직후 현상·증거·가설·결론을 바로 기록하면 기억에 의존한 추측을 줄일 수 있다.

# 튜토리얼: 이 미션을 이해하기 위한 핵심 개념

## 1. 프로그램, 프로세스, 스레드, PID

프로그램은 디스크에 있는 실행 파일이고, 프로세스는 그 파일이 메모리에 올라와 실행 중인 인스턴스다. PID는 프로세스의 번호표다. 스레드는 한 프로세스 안의 실행 흐름이다.

카페로 비유하면 매장 운영 매뉴얼은 프로그램, 실제 영업 중인 매장은 프로세스, 매장 번호는 PID, 주문·커피·포장을 동시에 담당하는 직원들은 스레드다. 매장은 열려 있어도 직원들이 서로 같은 도구를 기다리면 손님 주문은 멈출 수 있다. 이것이 "PID는 있지만 서비스는 멈춤"을 이해하는 출발점이다.

## 2. 가상 메모리, 힙, RSS와 메모리 누수

프로세스는 코드, 스택, 힙 등의 메모리 영역을 사용한다. 힙은 실행 중 크기가 변하는 객체를 저장하는 곳이다. 사용이 끝난 객체가 계속 참조되면 회수되지 않아 힙이 커진다. 이것이 메모리 누수다.

RSS(Resident Set Size)는 현재 물리 메모리에 올라온 프로세스 페이지 크기다. 앱이 말하는 `Current Heap`은 내부 논리 수치이고 `ps`의 RSS는 코드·라이브러리·스택 등도 포함한다. 그래서 두 숫자는 다르지만 누수 실험에서는 둘 다 장기적으로 상승하는지 본다.

현실 예시는 사용자 요청마다 1MB 이미지를 전역 배열에 넣고 삭제하지 않는 서버다. 초당 10개 요청이면 분당 약 600MB가 쌓인다. 처음에는 정상이어도 시간이 지나면 서버가 느려지고 결국 보호 정책 또는 OOM Killer가 프로세스를 종료한다.

## 3. OOM Killer와 애플리케이션 MemoryGuard의 차이

OOM Killer는 Linux가 시스템 메모리가 심각하게 부족할 때 프로세스를 골라 종료하는 최후 방어선이다. MemoryGuard는 애플리케이션 내부에서 자체 한계를 보고 더 일찍 자기 자신을 종료하는 정책이다.

이번 로그에 `[MemoryGuard]`와 `Self-terminating process`가 있으므로 직접 원인은 내부 정책이다. 보고서에는 "메모리 누수 → 내부 제한 도달 → MemoryGuard 자기 종료"로 써야 한다. 단순히 "OOM이 나서 Linux가 죽였다"고 쓰면 증거와 맞지 않는다.

## 4. CPU 사용률과 시스템 지연

CPU 사용률은 일정 시간 동안 프로세스가 CPU에서 실제 실행된 비율이다. 1개 코어 기준으로 한 프로세스가 100%면 그 코어를 거의 계속 쓰는 상태다. 멀티코어 시스템의 도구에 따라 한 프로세스가 100%를 넘게 표시될 수도 있다.

현실 예시는 메시지가 없는데도 `while true`로 큐를 계속 확인하는 코드다. `sleep`이나 이벤트 대기가 없으면 할 일이 없어도 CPU를 사용한다. 다른 프로세스는 실행 차례를 기다리므로 웹 요청 지연이 커진다. 해결은 단순히 임계치를 바꾸는 것이 아니라 바쁜 대기를 이벤트 기반 대기로 바꾸는 것이다.

## 5. Watchdog의 역할

Watchdog는 "정상 범위를 벗어나면 정해진 조치를 하는 감시자"다. CPU, 응답 시간, heartbeat를 감시하고 제한, 재시작, 트래픽 차단 등을 수행한다. 화재경보기처럼 문제 원인을 고치지는 않지만 피해 확산을 막고 명확한 사건 로그를 남긴다.

## 6. 데드락의 네 조건

교착상태는 다음 네 조건이 동시에 있을 때 가능하다.

1. 상호 배제: 자원을 한 번에 한 스레드만 사용한다.
2. 점유 대기: 자원 하나를 가진 채 다른 자원을 기다린다.
3. 비선점: 상대가 가진 자원을 강제로 빼앗을 수 없다.
4. 순환 대기: A가 B를, B가 A를 기다리는 원이 생긴다.

좁은 식당에서 두 사람이 각각 왼쪽 젓가락을 든 뒤 오른쪽 젓가락을 기다리는 상황과 같다. 둘 다 하나를 내려놓지 않으면 식사는 영원히 시작되지 않는다.

가장 단순한 예방은 모든 스레드가 항상 A 다음 B 순서로 락을 잡게 하는 것이다. 그러면 B를 먼저 가진 Thread-2가 생기지 않아 원이 끊어진다.

## 7. 프로세스 상태를 읽는 방법

Linux `ps`의 대표 상태는 다음과 같다.

- `R`: 실행 중 또는 실행 가능
- `S`: 인터럽트 가능한 대기, 정상적인 sleep/I/O 대기에도 흔함
- `D`: 인터럽트 불가 대기, 주로 커널 I/O
- `T`: 정지 또는 추적 중
- `Z`: 종료됐지만 부모가 회수하지 않은 좀비

상태 문자 하나만으로 데드락을 확정할 수 없다. CPU/RSS 변화, 스레드별 상태, 앱 진행 로그, 요청 응답 여부를 조합한다.

## 8. 좋은 장애 실험: 한 번에 한 변수

OOM을 볼 때 CPU와 스레드 설정도 위험하게 두면 CPU 종료나 데드락이 먼저 발생할 수 있다. 그래서 OOM 실험에서는 메모리만 바꾸고 CPU=10, 멀티스레드=false를 유지한다. CPU 실험과 Deadlock 실험도 같은 원칙을 쓴다.

과학 실험처럼 독립변수 1개, 관측값 여러 개, 동일한 시간 제한을 사용한다. 반복 실행에서 같은 패턴이 나오면 원인 설명의 신뢰도가 높아진다.

## 9. 로그를 증거로 만드는 법

좋은 로그 발췌에는 다섯 가지가 있다.

1. 언제: ISO 8601 또는 앱 타임스탬프
2. 무엇이: PID와 스레드 이름
3. 어떤 조건에서: 환경변수 값
4. 무슨 변화가: CPU/RSS/상태 수치
5. 어떤 결과로: 종료 코드, timeout, 핵심 메시지

한 줄만 떼어놓지 말고 정상 → 경고 → 장애의 앞뒤 3~10줄을 함께 보여준다. 전체 원본은 증거 파일로 남기고 보고서에는 핵심만 발췌한다.

## 10. GitHub Issue 형식으로 쓰는 이유

현상은 사용자가 겪은 결과, 증거는 재현 가능한 사실, 원인은 사실을 설명하는 기술적 추론, 조치는 위험을 줄인 행동과 검증이다. 이 순서를 지키면 동료가 "무슨 일이 있었나", "왜 그렇게 판단했나", "다시 확인할 수 있나"를 빠르게 알 수 있다.

나쁜 보고서는 "프로그램이 이상해서 재시작했다"로 끝난다. 좋은 보고서는 "09:00, PID 21, RSS가 25→50MB로 증가했고 MemoryGuard가 종료했다. 제한을 100MB로 바꾸자 생존 시간이 늘었지만 증가율은 같아 누수는 남았다"처럼 관측과 해석을 분리한다.

## 11. Before & After를 정직하게 해석하기

After에서 더 오래 살았다고 문제가 해결된 것은 아니다. 메모리 제한을 두 배로 올려 종료 시간만 두 배 가까이 늦어졌다면 오히려 누수가 계속된다는 강한 증거다. CPU 제한으로 종료가 사라져도 처리량이 낮아질 수 있고, 멀티스레드를 끄면 데드락은 피하지만 성능이 떨어질 수 있다.

따라서 리포트에는 임시 조치의 효과와 비용, 근본 코드 수정안을 모두 적는다.

## 더 깊이 이해하기: 장애 신호를 원인으로 연결하는 법

앞의 튜토리얼이 OOM·CPU Spike·Deadlock의 기본 현상과 재현법을 다뤘다면, 여기서는 같은 숫자가 서로 다른 원인에서 나올 때 어떻게 구분하는지에 초점을 맞춘다.

### 1. RSS 하나만으로 메모리 누수를 확정할 수 없는 이유

RSS에는 애플리케이션 힙뿐 아니라 스택, 공유 라이브러리의 resident page, 메모리 매핑 파일도 포함된다. Linux가 파일 캐시를 회수하거나 공유 page의 귀속을 계산하는 방식 때문에 RSS는 작업량이 늘 때 올라간 뒤 높은 수준을 유지할 수도 있다. 이것은 반드시 누수가 아니다.

더 세밀한 지표는 다음과 같다.

- `PSS`: 공유 page 비용을 공유 프로세스 수로 나눈 값
- `Private_Dirty`: 해당 프로세스만 쓰며 즉시 회수하기 어려운 변경 page
- cgroup의 `memory.current`: 컨테이너/서비스 경계에서 실제 청구되는 메모리
- allocation profile: 어떤 호출 경로가 객체를 계속 보유하는지 보여 주는 증거

```bash
awk '/^(Rss|Pss|Private_Dirty):/ {sum[$1]+=$2} END {for (k in sum) print k, sum[k] " kB"}' \
  /proc/$PID/smaps_rollup
```

현실 예시로 이미지 서버가 첫 요청에서 500MB 모델을 읽어 캐시하고 이후 500MB 근처에서 평평해진다면 warming일 가능성이 크다. 반대로 동일한 요청을 반복할 때 `Private_Dirty`와 live object 수가 매회 증가하고 유휴 시간에도 내려오지 않으면 누수 가설이 강해진다. 즉 **증가 후 plateau인지, 작업량에 비례해 제한 없이 증가하는지**를 본다.

### 2. CPU 100%는 원인이 아니라 결과다

프로세스 CPU가 높아도 상황은 다를 수 있다.

- 계산량이 실제로 많음: 압축·암호화·행렬 연산
- busy wait: 일이 없는데 조건을 계속 검사
- lock 경합: 짧은 락을 수많은 스레드가 반복 시도
- 재시도 폭주: 실패한 외부 호출을 지연 없이 다시 실행
- GC 압박: 객체 생성과 회수가 지나치게 잦음

반대로 cgroup 제한 때문에 CPU가 throttling되면 프로세스 CPU는 낮아 보이는데 요청 지연은 커질 수 있다. 은행 창구 직원이 게으른 것이 아니라 관리자가 매초 일할 수 있는 시간을 제한한 상황과 같다.

```bash
cat /sys/fs/cgroup/cpu.stat   # nr_throttled, throttled_usec 확인
cat /proc/pressure/cpu       # 일부 작업이 CPU를 기다린 시간 압력
pidstat -p "$PID" 1
```

따라서 `%CPU`와 함께 처리량, run queue/PSI, cgroup throttling, 함수별 profile을 연결해야 한다. CPU를 낮춘 뒤 요청 처리량도 절반이 되었다면 장애가 해결된 것이 아니라 단순히 일을 덜 하게 만든 것일 수 있다.

### 3. Deadlock·livelock·starvation은 겉모습이 비슷하다

세 경우 모두 "프로세스는 있지만 일이 끝나지 않는다"로 보인다.

| 현상 | 내부 움직임 | 현실 비유 | 구분할 증거 |
|---|---|---|---|
| deadlock | 서로의 자원을 기다려 멈춤 | 두 차가 서로 비키기만 기다림 | 고정된 wait-for cycle |
| livelock | 상태는 계속 바꾸지만 진전 없음 | 두 사람이 같은 방향으로 반복해 비킴 | CPU/로그 활동은 있으나 완료 수 0 |
| starvation | 일부 작업만 계속 기회를 못 얻음 | VIP 손님 때문에 일반 줄이 안 줄어듦 | 특정 요청의 대기시간만 무한 증가 |

앱 로그의 A→B, B→A는 deadlock을 설명하지만 실무 코드에서는 thread dump를 여러 시점에 채집해 같은 대기 관계가 유지되는지 확인한다. 한 장의 사진보다 10초 간격 사진 세 장이 "정지"를 더 잘 증명하는 것과 같다. Java라면 `jstack`, Go라면 goroutine dump, Python이라면 `faulthandler`처럼 런타임별 stack 증거를 사용한다.

### 4. wall clock과 monotonic clock의 역할은 다르다

ISO 시각은 여러 로그를 맞추는 데 좋지만 NTP 보정이나 관리자 변경으로 시간이 앞뒤로 움직일 수 있다. 실행 시간과 timeout을 벽시계 차이로 계산하면 실제 10초 작업이 음수나 40초로 기록될 위험이 있다.

- wall clock: `2026-09-03T10:00:00+09:00`처럼 사람이 사건을 대조할 때 사용
- monotonic clock: 부팅 이후 계속 증가해 경과 시간·timeout 계산에 사용

현실적으로 로그에는 둘 다 필요하다. "언제 발생했나"는 wall clock, "경고 후 몇 초 만에 종료됐나"는 monotonic duration으로 기록한다. 컨테이너 여러 개의 로그를 비교할 때는 timezone을 UTC로 통일하고, 보고서에서만 현지 시각으로 표시하면 혼동이 줄어든다.

### 5. 장애 격리는 자원별 보호보다 한 단계 넓은 설계다

MemoryGuard나 CPU 제한은 한 프로세스가 호스트 전체를 망가뜨리는 것을 줄인다. 그러나 재시작된 프로세스가 같은 문제를 즉시 반복하면 restart storm이 되어 오히려 의존 서비스와 로그 시스템을 압박할 수 있다.

실무에서는 여러 보호 장치를 조합한다.

- **backpressure**: 처리 능력보다 요청이 많으면 무한 적재 대신 거절하거나 생산자를 늦춘다.
- **bulkhead**: 작업 종류별 worker pool을 나눠 한 종류의 정체가 전체를 막지 않게 한다.
- **circuit breaker**: 실패하는 의존 서비스 호출을 잠시 중단해 재시도 폭주를 막는다.
- **restart backoff**: 재시작 간격을 점차 늘리고 일정 횟수 뒤 운영자 개입을 요구한다.

예를 들어 이미지 변환 작업이 메모리를 모두 써도 로그인 요청용 worker와 quota가 분리되어 있으면 사용자는 계속 로그인할 수 있다. 이것이 단순한 "프로세스 종료"를 넘어 장애 반경(blast radius)을 줄이는 접근이다.

### 6. 한 변수 실험도 반복과 대조군이 있어야 강해진다

한 번의 Before/After는 우연한 트래픽, 캐시 warming, CPU 배치 차이의 영향을 받을 수 있다. 더 신뢰할 수 있는 실험은 정상 대조군과 장애 조건을 같은 순서·시간으로 여러 번 실행하고 다음을 비교한다.

```text
control 3회: 종료까지 시간 = 없음, RSS 기울기 ≈ 0 MB/min
fault   3회: 종료까지 시간 = 31s, 29s, 32s, RSS 기울기 ≈ 18 MB/min
```

결과를 단순 PASS가 아니라 `효과 크기 + 변동성`으로 기록하면 재현성을 설명할 수 있다. 환경 변수 값을 바꾼 후 종료만 사라지고 RSS 기울기가 그대로라면 보호 임계치만 늦춘 것이며, 기울기까지 0에 가까워져야 누수 원인 수정이라는 주장이 가능하다.

## 실무에서 바로 쓰는 접근법

### 접근법 1. 첫 5분에는 복구와 증거 보존을 동시에 설계한다

장애 인스턴스를 로드밸런서에서 제외해 사용자 피해를 줄인 뒤, PID·시작 시각·자원 snapshot·최근 로그·thread dump를 정해진 스크립트로 빠르게 수집한다. 그 다음 재시작한다. 메모리가 고갈 직전이면 긴 profile보다 짧은 증거만 남기고 가용성을 우선한다. 이 우선순위를 runbook에 미리 적어 두면 사고 중 판단 시간을 줄일 수 있다.

### 접근법 2. 신호를 `사용자 → 서비스 → 런타임 → 커널` 순으로 연결한다

먼저 오류율·지연·처리량으로 실제 영향을 확인하고, 서비스 queue와 완료 수, 런타임 heap/GC/thread, 마지막으로 RSS·PSI·cgroup 이벤트를 본다. 커널 CPU 100%만 보고 앱을 범인으로 정하는 대신 각 층의 시간축이 맞는지 확인한다. 서로 다른 두 층 이상에서 같은 가설을 지지할 때 원인 확신도를 높인다.

### 접근법 3. 완화와 근본 해결에 서로 다른 완료 조건을 둔다

멀티스레드 비활성화로 deadlock이 사라진 것은 완화 완료다. 전역 lock order 적용, 동시성 회귀 테스트, 정상 처리량 회복까지 확인해야 근본 해결 완료다. OOM과 CPU도 각각 "프로세스 생존"만 보지 말고 메모리 증가 기울기와 요청당 CPU가 개선됐는지 검증한다. 이 구분이 임시 설정이 영구 해결책으로 굳는 일을 막는다.
